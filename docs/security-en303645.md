# openccu-lite against ETSI EN 303 645

The product baseline: ETSI EN 303 645 (*Cyber Security for Consumer Internet of Things: Baseline Requirements*, V2.1.1
and the V3.1 draft's numbering, which is the same at the provision level) has thirteen groups of provisions for the
device and its services (5.1–5.13) and a group of data protection provisions (6). Each row below is one group, in our
own words, with the verdict and where the answer is. The standard maps onto the essential requirements of the EU Cyber
Resilience Act; which of those fall on an open-source project is a separate question, and this is not legal advice.

**Verdicts:** `pass` — the provisions of the group are met; `partial` — some are, the gap is named; `fail` — not met,
with the item that tracks it; `n.a.` — not applicable, with the reason. The items named (`B-n`, `task n`) are the
project's roadmap items.

**As of:** occulited `2412769`, image `1.0.0-dev.28`, 2026-09-26 (task 120's phase 5; the rows follow phase 3's second
pass of the same day, with the secret files' modes and the TLS settings measured on a lab system). The verification checklist for
the code is [security-asvs.md](security-asvs.md); the threat model is [threat-model.md](threat-model.md).

| provision | in our words | verdict | where, and why |
| --- | --- | --- | --- |
| **5.1** no universal default passwords | no shared or predictable default password; per-device or user-set credentials; authentication values from a CSPRNG; resistance against brute force | pass | the first boot forces an administrator account with a user-set password (`Store.Setup`); the image ships no account with a password; sessions and tokens come from `crypto/rand` (130 / 128 bits); the lockout after 8 failures for 15 minutes (the address half by lighttpd's address since **B-230**'s fix). SSH is off unless the administrator switches it on (`sshd.service` exits when it is off; task 185), and then root's password is the account's — key-only login is task 245 |
| **5.2** manage vulnerability reports | a public disclosure policy with a contact, timely handling, and a way to tell users | pass | `SECURITY.md` in the repository (task 258: GitHub private vulnerability reporting, supported versions); GitHub Security Advisories with CVE ids are the channel to users; release notes credit reporters. The response times promised there are the maintainer's |
| **5.3** keep software updated | updates are possible, simple for the user, authenticated (integrity and authenticity), timely; the user is told when an update is available and what it changes; security updates for a defined support period; the update mechanism does not break the device | partial | the Updates page and the release check (daily; the version, the notes); a staged install through the recovery system with the Status page watching the system come back; the checksum of the release is verified — **but the release is not signed** (F-7, R3): the sum comes from the same host as the file. **Task 263** (minisign, the key in the image) closes it. The support period is a statement the README owes (task 258) |
| **5.4** securely store sensitive security parameters | secrets stored so that only what needs them reads them; no hard-coded credentials; device identity keys unique per device | partial | passwords argon2id; tokens SHA-256; sessions 0600 in a 0700 directory; `occulited.json` and the state directory owned by `occulite` with `UMask=0077`; the radio keys, `crypttool.cfg` and hmipserver's key store owned by root or the daemons' users after task 67; the OIDC client secret and the ACME account key in the state directory. **The radio keys are in clear on the storage and in every backup** — R6, accepted because hmipserver needs them so; encrypted backups exist (task 91, age with a recovery key) and are the user's choice. Nothing is hard-coded. **Measured on a lab system (dev.28):** occulited's state `drwx--x--x` with 0600 files, the ACME account key and the TLS key 0600, the backup identity 0700 and out of every backup, `keys` `rfd` 0600, `server.pem` `root:certs` 0640 (D-46); two findings about file modes on the system are under review (**B-252**, **B-253**) |
| **5.5** communicate securely | best-practice cryptography for communication; unauthenticated access to security parameters or device functions is not possible over the network; authenticated management | partial | lighttpd offers HTTPS with TLS 1.2 as the minimum (`sslsettings.conf`) and ACME for a real certificate; **HTTP is the default** (a self-signed certificate at first, the redirect to HTTPS and HSTS are options) — the usual state of a LAN device, stated in [security.md](security.md). Everything that is not the web door listens on the loopback (D-29): occulited, the interface processes, lite-rpc. Classic RPC is the CCU's protocol without authentication and is a switch that is off by default with a warning (R8). The outbound calls verify TLS against the four trust stores (task 231). **Measured on a lab system:** TLS 1.0/1.1 refused, TLS 1.2 `ECDHE-ECDSA-AES256-GCM-SHA384`, TLS 1.3 `TLS_AES_256_GCM_SHA384`, CBC and static-RSA suites refused |
| **5.6** minimise exposed attack surfaces | unused ports closed; services not exposed unless needed; least privilege for software; hardware debug interfaces disabled; code minimised to what is needed | partial | the firewall defaults to `RESTRICTIVE` and only lighttpd faces the LAN (D-9, D-28, D-29); hmipserver's 9293/9294 and UDP 43438 are closed unless an access point is present (D-55); SSH off by default. occulited runs as `occulite` behind a root helper with an allowlist (task 17); its unit is sandboxed (task 208: `systemd-analyze security` 8.3 → the directives in `occulited.service`), lighttpd's unit too; addons are confined by default (D-36); the interface processes got their own users (task 67). **Gaps:** the eQ-3 processes remain black boxes, occulited is not PIE and three C programs have partial RELRO (**task 261**), the serial console is a login on the Raspberry Pi as on every OpenCCU (physical access, R7); lighttpd's connection limits are upstream's (**B-254**) and a leftover world-writable directory of the CCU remains (**B-257**, low); a confined addon may no longer declare a root-equivalent capability or the privilege helper's group (**B-251** fixed); `checkFirmwareUpdate.sh` shipped without a caller until **B-244** |
| **5.7** ensure software integrity | the software is verified with secure boot or an equivalent; unauthorised changes are detected and the user alerted | partial | a read-only root filesystem with the userfs apart; the recovery system checks a release's kind and board and its sum before installing it (B8). There is no secure boot on the Raspberry Pi or the OVA, and **no signature** on releases — **task 263** is the equivalent the standard allows for. A modified root is not detected at runtime |
| **5.8** ensure personal data is secure | personal data in transit is protected; the user is told what is sent to whom (see 6) | pass | every outbound connection, field by field, with its switch, is in [privacy.md](privacy.md); the requests occulited builds are pinned by tests (`internal/*/outbound_test.go`), so a change to what leaves the system is a visible diff. In transit: HTTPS to GitHub, eQ-3, the key server and the CAs; the syslog forward (UDP) and MQTT (plain TCP) are opt-in and LAN-bound by intent, and privacy.md says so. The daily checks are off on a fresh system and asked once on the welcome page, destination by destination; the catalogue is read from the copy of the last check and the shipped copy, never fetched by opening a page (B-240, B-241) |
| **5.9** make systems resilient to outages | the device keeps working without the network and recovers cleanly from power loss | pass | nothing depends on a cloud: the radio stack and the web UI work with no internet; the userfs is journalled (ext4) and the root read-only; systemd restarts the daemons (`Restart=always` with back-off); the watchdog marker and the boot expectation (`occu-watchdog-marker.service`, `internal/bootexpect`) bring a failed update or a hung boot back to the last good system; the clock is saved hourly and restored at boot for systems without an RTC. HmIP's local key mode (task 149) removes the dependency on eQ-3's key server for pairing |
| **5.10** examine system telemetry data | if telemetry is collected, it is examined for security anomalies | pass | there is no telemetry to a vendor. The system's own journal is the telemetry the administrator has (the Log page, the warnings on Status); logins, refused logins and lockouts are in it at the default level since **B-231**'s fix (2026-09-26) |
| **5.11** make it easy for users to delete user data | the user can erase personal data from the device and from any service; clear instructions | pass | the factory reset from the web UI (task 109: the userfs wiped, with the warning about paired BidCos devices and an individual key), the account and token deletion routes, and the metadata store's own delete operations; no vendor service holds user data, so there is nothing to erase elsewhere |
| **5.12** make installation and maintenance easy | installation with minimal decisions and secure defaults; guidance on secure setup; a way to check the security state | pass | the first boot's setup (one account), the Status page's warnings (an unencrypted backup target, classic RPC without login, a public Control app, a failing trust chain, an update available) and the help texts are the checks; the secure defaults are 5.6's. `docs/switching.md` and the README carry the setup guidance |
| **5.13** validate input data | data from the network, uploads and outside sources is validated | partial | every API body is JSON with a schema check, names refuse control characters (B-38), the archive readers drop climbing members and links and cap sizes, the helper's allowlist checks every path at the boundary; every JSON body has a size limit (**B-232**, fixed 2026-09-26); the uploads have ceilings and land in a staging directory on the userfs under names the system chooses — the regadom import moved there too (**B-255** fixed), with one exception left (the system-update upload's cap, **B-256** low); the reverse proxy's own body handling is under review (**B-239**); no fuzz tests yet (**task 265**) |
| **6** data protection provisions | the consumer is told what personal data is processed, by whom and why; consent for telemetry; easy withdrawal; sensor data processed transparently | pass | no telemetry, no vendor account, no cloud; the personal data on the device are the household's own (names, rooms, values, the journal) and leave it only in the user's backups and, opt-in, the syslog forward and MQTT. [privacy.md](privacy.md) is the statement: what goes to GitHub, eQ-3 (the paired device types that need a firmware update; SGTINs to the key server), a CA and an OIDC provider, when, and how to switch each off |

## What this baseline says, in one paragraph

openccu-lite has no default password, no cloud and no telemetry, one door to the LAN, a sandboxed system service behind
a root helper with an allowlist, confined addons, a factory reset and a disclosure policy — the provisions that are about
the product's shape are met. What it still owes is **signing** (5.3, 5.7 — task 263) and the
smaller hardening items (5.6 — task 261, B-254; 5.13 — task 265), and the findings of the audit's second pass that are under review (B-239, B-252 to B-254); the audit trail at the default level (5.10 — B-231), the body
limits (5.13 — B-232) and the privacy statement ([privacy.md](privacy.md), 5.8, 6 — task 266) landed on 2026-09-26. HTTPS by default is a question the standard does not force for a LAN device but a user who
forwards a port should read [security.md](security.md) first.
