# openccu-lite against ETSI EN 303 645

The product baseline: ETSI EN 303 645 (*Cyber Security for Consumer Internet of Things: Baseline Requirements*, V2.1.1
and the V3.1 draft's numbering, which is the same at the provision level) has thirteen groups of provisions for the
device and its services (5.1–5.13) and a group of data protection provisions (6). Each row below is one group, in our
own words, with its status and where the answer is. It describes what the code does; <ins>**it is not a certification
or a statement of conformity.**</ins> The standard maps onto the essential requirements of the EU Cyber Resilience Act;
which of those fall on an open-source project is a separate question, and this is not legal advice.

**Status:** ✅ met as we read the group; ⚠️ partly met — the text says what is missing, or what is accepted and why.

**As of:** 1.1.0-dev.6 (occulited `99133b04`), 2026-10-30. The verification checklist for the code is
[security-asvs.md](security-asvs.md); the threat model is [threat-model.md](threat-model.md); the user's summary is
[security.md](security.md).

| provision | in our words | status | where, and why |
| --- | --- | --- | --- |
| **5.1** no universal default passwords | no shared or predictable default password; per-device or user-set credentials; authentication values from a CSPRNG; resistance against brute force | ✅ | The first boot forces an administrator account with a user-set password (`Store.Setup`); the image ships no account with a password. Sessions (130 bits) and tokens (128 bits) come from `crypto/rand`. The lockout after 8 failures for 15 minutes, per name and per client address (lighttpd's, not a client-sent header). SSH is off unless the administrator switches it on (`sshd.service` exits while it is off); root's password is then the administrator's to set, and an option refuses password logins (keys only) |
| **5.2** manage vulnerability reports | a public disclosure policy with a contact, timely handling, and a way to tell users | ✅ | `SECURITY.md` in the repository: GitHub's private vulnerability reporting, what is in scope, which versions get fixes. GitHub Security Advisories are the channel to users; release notes credit reporters |
| **5.3** keep software updated | updates are possible, simple for the user, authenticated (integrity and authenticity), timely; the user is told when an update is available and what it changes; security updates for a defined support period; the update mechanism does not break the device | ⚠️ | **Missing: authenticity** — releases are not signed; the SHA-256 is published by the same host as the file (threat model R3). **Missing: a support period in years**; `SECURITY.md` says which line gets fixes. In place: the Updates page and the release check (daily when switched on; update channels stable, beta and dev; the release notes linked); a Status warning when an update is available; the download checked against the published SHA-256 (a sum file that cannot be read fails the download; a release without one is staged with a warning that it is not verified); the file's kind read from its content and the space checked at staging and at install; the recovery system's own checks of kind, board and space; the Status page watching the system come back; `occulited update` on the command line |
| **5.4** securely store sensitive security parameters | secrets stored so that only what needs them reads them; no hard-coded credentials; device identity keys unique per device | ⚠️ | **Accepted: the radio keys are stored in clear** on the storage and in every unencrypted backup, because hmipserver needs them so (R6); encrypted backups (age, with a recovery key) are the user's choice. In place: passwords argon2id, tokens SHA-256, sessions kept only as hashes; occulited's state owned by `occulite` with 0600 files (`UMask=0077`), the ACME account key, the DNS provider credentials and the OIDC client secret among them; `/etc/config/keys` rfd's 0600; hmipserver's key and device files 0700/0600, tightened at every start; `server.pem` `root:certs` 0640 — readable by confined addons by design, so a broker can use it; the backup identity outside every backup. Nothing hard-coded |
| **5.5** communicate securely | best-practice cryptography for communication; unauthenticated access to security parameters or device functions is not possible over the network; authenticated management | ⚠️ | **Not by default: HTTPS is an option, HTTP the default** (a self-signed certificate at first; the redirect to HTTPS and HSTS are switches) — the usual state of a LAN device, stated in [security.md](security.md). **Accepted:** classic RPC is the CCU's protocol without real authentication — a switch that is off by default, with a warning (R8); the Control app's public mode lets anyone who reaches the web port operate devices — off by default, warned about on Status. In place: lighttpd with TLS 1.2 as the minimum, TLS 1.3, AES-GCM/ChaCha20 suites only (`sslsettings.conf`; measured: TLS 1.0/1.1, CBC and static-RSA suites refused); ACME for a real certificate (HTTP-01 or DNS-01); everything that is not the web door listens on the loopback; every API route needs a session or a token with its scope; outbound calls verify TLS against the system's trust stores |
| **5.6** minimise exposed attack surfaces | unused ports closed; services not exposed unless needed; least privilege for software; hardware debug interfaces disabled; code minimised to what is needed | ⚠️ | **Missing:** the Raspberry Pi's serial console offers a login, as on every OpenCCU (physical access, R7); eQ-3's daemons are binaries we cannot audit. In place: the firewall's policy DROP, one owned rule per feature; only lighttpd faces the LAN; the HmIP access points' ports and SSH closed unless needed; occulited runs as `occulite` behind a root helper with an allowlist, in a sandboxed unit; lighttpd runs as `www-data` with `CAP_NET_BIND_SERVICE` alone; the interface daemons run as their own users with no capabilities; addons are confined by default and a confined addon may not declare a root-equivalent capability or group; root addons without `CAP_SYS_ADMIN`; seccomp-enforced unit settings; the C programs PIE with the stack protector, FORTIFY and RELRO, lighttpd, busybox and chronyd with full RELRO, checked at every build (`scripts/lite-hardening-guard.sh`; occulited is a static Go binary, not a PIE) |
| **5.7** ensure software integrity | the software is verified with secure boot or an equivalent; unauthorised changes are detected and the user alerted | ⚠️ | **Missing:** secure boot, signed releases, and detection of a modified root at runtime. There is no secure boot on the Raspberry Pi or the OVA, and no signature on releases — signing is the equivalent the standard allows for. In place: a read-only root filesystem with the userfs apart; the checksum and the recovery system's checks before an install (threat model B8) |
| **5.8** ensure personal data is secure | personal data in transit is protected; the user is told what is sent to whom (see 6) | ✅ | Every outbound connection, field by field, with its switch, is in [privacy.md](privacy.md); the requests occulited builds are pinned by tests (`internal/*/outbound_test.go`), so a change to what leaves the system is a visible diff. In transit: HTTPS to GitHub, eQ-3, the key server, the CAs, the DNS providers and the identity provider; the syslog forward (UDP) and MQTT are opt-in and LAN-bound by intent, and privacy.md says so. The daily checks are off on a fresh system and asked once on the welcome page; the catalogue is read from the copy of the last check and the shipped copy, never fetched by opening a page |
| **5.9** make systems resilient to outages | the device keeps working without the network and recovers cleanly from power loss | ✅ | Nothing depends on a cloud: the radio stack and the web UI work with no internet; local key mode removes the dependency on eQ-3's key server for a module exchange and pairing. The userfs is journalled (ext4) and the root read-only; systemd restarts the daemons and reports a crash loop instead of hiding it; the watchdog marker and the boot expectation (`occu-watchdog-marker.service`, `internal/bootexpect`) bring a failed update or a hung boot back to the last good system; the clock is saved hourly and restored at boot for systems without an RTC; on a Raspberry Pi 2/3 B the kernel resets the LAN9514 USB hub at every boot, and one that is still missing before the network starts gets its USB port re-powered (`lite-lan-reset`) |
| **5.10** examine system telemetry data | if telemetry is collected, it is examined for security anomalies | ✅ | There is no telemetry to a vendor. The system's own journal is the telemetry the administrator has (the Log page, the warnings on Status): logins, refused logins and lockouts at the default level, every system change with its user and address, every refusal of the privilege helper |
| **5.11** make it easy for users to delete user data | the user can erase personal data from the device and from any service; clear instructions | ✅ | The factory reset from the web UI (the userfs wiped, with the warning about paired BidCos devices and an individual key), the account, passkey and token deletion routes, and the metadata store's own delete operations; no vendor service holds user data, so there is nothing to erase elsewhere |
| **5.12** make installation and maintenance easy | installation with minimal decisions and secure defaults; guidance on secure setup; a way to check the security state | ✅ | The first boot's setup (one account) and the welcome page's choices; the Status page's warnings (an unencrypted backup target, an unset BidCos key with BidCos devices paired, classic RPC without login, a public Control app, a failing trust chain, an update available) and the help texts are the checks; the secure defaults are 5.6's and [security.md](security.md)'s overview; `docs/switching.md` and the README carry the setup guidance |
| **5.13** validate input data | data from the network, uploads and outside sources is validated | ⚠️ | **Missing:** fuzz tests for the parsers of outside data; lighttpd does not refuse invalid UTF-8 in a URL. In place: lighttpd refuses control characters in a URL; every API body is JSON with a schema check and a size limit; names refuse control characters; the archive readers drop climbing members and links and cap sizes; the uploads have ceilings and land in a staging directory on the userfs under names the system chooses; the reverse proxy streams every body; the helper checks every path at the boundary; the manifest is validated field by field |
| **6** data protection provisions | the consumer is told what personal data is processed, by whom and why; consent for telemetry; easy withdrawal; sensor data processed transparently | ✅ | No telemetry, no vendor account, no cloud; the personal data on the device are the household's own (names, rooms, values, the journal) and leave it only in the user's backups and, opt-in, the syslog forward and MQTT. [privacy.md](privacy.md) is the statement: what goes to GitHub, eQ-3 (the paired device types that need a firmware update; SGTINs to the key server unless in local key mode), a CA, a DNS provider and an identity provider, when, and how to switch each off |

## What this baseline says, in one paragraph

openccu-lite has no default password, no cloud and no telemetry, one door to the LAN, a sandboxed system service behind
a root helper with an allowlist, interface daemons and addons under their own users, a factory reset, a privacy
statement and a disclosure policy. What it still lacks is **signing** (5.3, 5.7), a support period in years (5.3),
fuzz tests and a check for invalid UTF-8 in URLs (5.13). HTTPS by default is a question the standard does not force for a LAN
device, but a user who forwards a port should read [security.md](security.md) first.
